# Agent 观测纪律（编排器通用机制与制度）

> 适用：任何「编排方驱动终端内 coding agent」的场景——tern、herdr 及同类。
> 本文沉淀机制与制度；命令映射见 §5，实验证据与定案记录见 `tern-capture-active-spec.md`、`omp-capture-issue.md`。

## 1. 验证四问，各走各的通道

| 问题 | 通道 | 形态 | 编排方上下文成本 |
|---|---|---|---|
| 返回了什么 | 结构化共享存储（项目信箱/DB） | 几行记录 | 极低 |
| 干完没 | 输出流静默判定（idle 门） | 退出码，无文本 | 零 |
| 活没活 | 进程/状态结构化查询 | 一行 JSON | 极低 |
| 卡哪了 | **读屏（按需一眼）** | 整帧终端文本 | 高（与帧大小成正比） |

原则：**内容验证以共享存储为契约，不以屏幕为契约**。屏幕是给人看和排障用的，不是编排方回收结果的通道。

## 2. 读屏 = 排障工具，不是监控

- 读屏返回整帧终端文本；TUI 形态的 agent 连**推理全程**一起返回。每次读屏都整段进入编排方上下文——token 成本只与帧大小相关，与信息是否有用无关。
- 合法使用时机只有三个：等待超时、怀疑死循环/卡审批、需要肉眼看现场。
- **禁止**轮询读屏充当监控；多任务用事件流订阅（或状态查询），内容回收用信箱等待。

## 3. 可见性与功能解耦

- 空屏 ≠ 死亡，≠ 没干活。agent 帧不可见时，它可能正正常常地收信、执行、回信（实证：omp 原生交互模式下信箱全链路通）。
- 屏幕可见性受**两层开关**影响：编排器的版本代次（defect 修复）+ **agent 自身渲染形态**（TUI vs 原生/内联）。第二层与编排器无关，是 agent 侧变量。
- 制度：读屏为空时的排查顺序 = 编排器版本 → agent 渲染形态 → 进程判活 → 静默门判完成 → 回退共享存储回收。**不得**因空屏判死，**不得**盲发第二遍。

## 4. 注入前安检按 agent 类型分流

- 有审批/提问框的 agent：读屏查审批文案，命中即停、上报人决断，不代按。
- 无审批框的 agent：静默门即安检；屏检无从判断也无必要。
- 共同底线：**忙时注入 = 事故**。静默门走输出流、与渲染形态无关，是所有 agent 的兜底。

## 5. 机制 → 命令映射

| 机制 | tern | herdr |
|---|---|---|
| 内容回收（信箱） | `agentmsg read` / `inbox` | 同一信箱（同一套命令） |
| 完成判定（静默门） | `tern wait <id> --until idle=MS` | `herdr agent get` 生命周期状态（仅 idle/done 可投） |
| 活没活 | `tern process <id> --json` | `herdr agent get` |
| 卡哪了（读屏） | `tern capture <id> [--scrollback] [--ansi]` | `herdr agent read <target> --source recent-unwrapped` |
| 监控 | `tern events` 订阅 | 状态查询（勿轮询读屏） |
| 注入 | `tern send paste` + `keys enter` | `herdr agent prompt`（原子提交） |
