# Herdr 与 Tern 更新后的消息投递安全与兼容性

Status: ready-for-agent

## Problem Statement

使用 agentmsg 协调多个 Agent 时，用户需要知道 watcher 何时可以向目标终端提交消息通知，以及「已投递」「已读」「任务完成」分别代表什么。当前 Herdr 接入文档将结构化状态描述为「零歧义」，但 Herdr 官方说明指出 `idle` / `done` 无法保证识别所有审批界面，也无法保证保留身份的 Agent 在前台。Herdr 0.9.5 的 Codex 状态来源和 Claude Code 问题识别修复也会影响状态判断。

Tern 投递依赖输出静默和屏幕关键词。现有观察中，一个 pane 静默约 76 秒时 `tern inspect` 仍返回 `working=true`；这提示静默不能单独证明任务完成。该字段的来源、支持范围和状态转换尚未验证，不能直接把它作为可靠的通用生命周期状态。Tern 0.9.5 到 0.9.8 的逐版更新记录也未取得，不能把当前接口直接归为新增能力。

用户需要一套有证据支持的版本说明与投递判断，避免消息进入忙碌的 Agent、审批界面或错误的前台进程，并保留无法确定是否送达时的恢复方式。

## Solution

校正 Herdr 0.9.5 与 Tern 0.9.8 的现状和安全边界；在隔离环境中验证两者的可观察状态及适用范围。对已有 watcher 投递路径，只在证据支持且能识别目标的情况下，将可用的忙碌信号作为额外的暂缓条件。状态不可可靠判断时明确保留现有限制，不能将未经验证的字段解释成确定的 Agent 就绪信号。

SQLite 信箱继续保存消息状态，终端只负责通知；以消息 ID 关联取信和回执。通过现有单次投递入口验证消息状态、通知内容和拒绝投递行为，并以隔离的真实终端场景核对关键状态。

## User Stories

1. 作为协调多个 Agent 的用户，我希望知道本机使用的 Herdr 和 Tern 版本，以便判断适配说明的适用范围。
2. 作为维护者，我希望区分官方版本更新和当前可见功能，以便不把旧功能误认为新功能。
3. 作为维护者，我希望知道 Herdr 客户端与服务端可能版本不同，以便排查不兼容行为。
4. 作为 Codex 用户，我希望知道 Herdr 的 Codex 状态可能来自屏幕识别，以便理解状态识别的限制。
5. 作为 Claude Code 用户，我希望问题界面被识别为 `blocked` 时暂停投递，以便避免通知进入审批界面。
6. 作为用户，我希望知道未知审批界面可能未被识别，以便在授权和投递时保持判断。
7. 作为用户，我希望知道挂起 Agent 后保留的身份不保证其处于前台，以便避免误向其他进程发送输入。
8. 作为用户，我希望知道 Agent 报告空闲时其后台任务仍可能运行，以便不把空闲等同于全部工作完成。
9. 作为 watcher 使用者，我希望 `working`、`blocked` 和 `unknown` 的 Herdr 目标保持消息待投递，以便稍后安全处理。
10. 作为 watcher 使用者，我希望无效或缺失的 Herdr 状态不触发投递，以便避免依赖错误数据。
11. 作为 Tern 用户，我希望知道输出静默只说明一段时间没有输出，以便不把静默当成 Agent 已完成。
12. 作为维护者，我希望验证 Tern `working` 的来源和状态转换，以便判断它能否阻止对忙碌 Agent 的投递。
13. 作为维护者，我希望分别验证目标 Agent 和渲染形态对 Tern 状态的影响，以便明确结论的适用范围。
14. 作为维护者，我希望检查 Tern 状态能否与已注册 block 准确对应，以便不因窗口或目标混淆而向错误 pane 投递。
15. 作为用户，我希望在可靠的忙碌信号成立时消息保持 `pending`，以便空闲后继续投递。
16. 作为用户，我希望无法验证的 Tern 状态不会被宣传为可安全投递的证明，以便理解剩余风险。
17. 作为用户，我希望屏幕采集为空时仍能知道其局限，以便不误判 Agent 已退出或已空闲。
18. 作为用户，我希望待审批界面不被自动输入通知或确认按键，以便授权仍由人决定。
19. 作为收件 Agent，我希望终端通知只包含消息 ID 和固定取信指引，以便正文不会被注入到当前界面。
20. 作为发送方，我希望 `delivered` 仅表示终端接受通知，以便不误以为收件 Agent 已读。
21. 作为发送方，我希望通过 `read` 和 `reply` 判断取信与回执，以便确认消息处理进展。
22. 作为收件 Agent，我希望按消息 ID 识别重复通知，以便提交超时后的重试不会重复执行任务。
23. 作为维护者，我希望认领租约和 fencing 在跳过或失败时继续生效，以便并发 watcher 不破坏消息状态。
24. 作为用户，我希望重绑后的 watcher 使用最新目标，以便消息不会继续投向过期 pane。
25. 作为维护者，我希望用现有单次投递入口验证外部行为，以便覆盖数据库状态和终端提交的完整契约。
26. 作为维护者，我希望隔离场景覆盖空闲、忙碌和审批状态，以便区分 mock 行为和真实终端行为。
27. 作为用户，我希望知道哪些版本和场景经过真实验证，以便不把推测当作兼容性承诺。
28. 作为维护者，我希望运行环境不满足时保留验证限制和证据，以便后续可以复现，而不是报告虚假的通过。

## Implementation Decisions

- 保留现有 SQLite 信箱、消息状态、认领租约、fencing 和 watcher 单次投递入口；不引入第二套队列或新的公共适配器抽象。
- 更新 Herdr 接入说明、适配器说明和观察纪律：结构化状态是识别结果，不保证识别所有审批界面或前台进程；`idle` / `done` 不证明后台任务结束。
- 保留 Herdr 已有 `idle` / `done` 状态门、未知状态拒绝投递、`HERDR_ENV=1` 限制及 `agent prompt` 的现有提交语义。记录查询与提交之间状态可能改变；不声称这些措施消除了误投风险。
- 描述 Herdr 0.9.5 为 0.9.4 的修复版，记录 Codex 状态来源变化和 Claude Code 命名会话问题识别修复；不自动修改用户的 Herdr 集成。
- 在隔离环境中检查 Tern `inspect` 的目标匹配、`working` 字段来源、类型及空闲、工作、静默工作、审批、退出等状态变化；按实际支持的 Agent 和渲染形态记录结果。查询不得控制或读取用户现存 pane 的私有内容。
- 若验证证明某一目标及 Agent 类型的 `working=true` 可可靠表示忙碌，可将它作为该范围内的额外暂缓条件；保留既有静默门和审批检测，且不将 `working=false` 视为完成或安全的证明。若字段缺失、查询失败或适用性未验证，不得把这些情况解释为安全状态；具体兼容处理须以已验证接口为依据，避免声称覆盖未验证范围。
- 保持固定通知只含可信消息 ID 和取信指引；不加入消息正文、主题或发送方等用户可控内容。
- 保持 `pending`、`claimed`、`delivered`、`read`、`done` 的现有语义：`delivered` 只代表提交被终端接受；提交失败或超时可能已送达，收件 Agent 按消息 ID 去重。
- 不改数据库 schema、既有注册参数或跨 transport 切换方式；目标绑定以现有注册表为准，每次投递重新读取。
- 文档中的版本结论区分官方发布说明、本机 CLI 输出与隔离实验；无法取得 Tern 逐版发布说明时明确记为证据缺口。

## Testing Decisions

- 主要测试边界为现有 watcher 的单次投递入口：从已注册目标与待投递消息出发，观察消息状态和外部可见通知；避免新增仅为测试而设的公开接口。
- 好的测试覆盖可观察行为、状态转换和失败边界，而不固定内部调用顺序或实现细节。沿用现有临时 SQLite 数据库与模拟终端命令的测试方式，参考已有 Tern 和 Herdr 投递测试。
- 覆盖 Herdr 的已知忙碌、审批、未知或不可解析状态不投递且消息保持 `pending`；成功提交只写 `delivered`，通知不含正文；提交结果不明时不宣称未送达。
- 对经过真实验证后纳入的 Tern 忙碌条件，覆盖静默但忙碌时暂缓、状态和目标不匹配时不误投，以及查询异常和字段缺失的明确行为；不以 `working=false` 单独证明可投。
- 在隔离 session 或自建 pane 中进行真实验证：记录工具版本及客户端/服务端信息，分别观察空闲、工作中、静默工作和可构造的审批场景；只操作自己创建的目标。
- 如果无法构造某个 Agent、审批 UI 或渲染形态，应记录未覆盖场景及原因；mock 测试通过不等于真实终端兼容。
- 不以截图或整段终端转录作为常规完成判据；内容回收走信箱，必要时按需读取现场。

## Out of Scope

- 宣称覆盖所有 Agent、所有审批界面或实现 exactly-once 投递。
- 重写 SQLite 信箱、引入新队列、增加跨机器路由或改变用户授权流程。
- 自动安装、升级或重启 Herdr/Tern、更新 Codex 集成、关闭用户 pane。
- 基于缺失的发布记录推测 Tern 逐版更新内容。
- 开发浏览器自动化、插件或与本投递问题无关的终端功能。

## 原型实验记录（2026-10-30）

- 本机 `tern 0.9.8 (f21d9a3)`：在新建的隔离会话中，PowerShell 执行 30 秒静默等待时，`inspect` 对该 pane 返回 `working=false`，同时 `quiet_ms` 约 9585；该字段不能作为通用进程忙碌判断。
- 隔离 omp pane 曾报告 `working=true`，之后报告 `false`；因画面采集为空，不能确认两次观察与实际任务阶段的对应关系，也不能据此推断审批状态或其他 Agent 类型的行为。
- 原型是可交互的假设模型，已验证「已验证目标 + 静默 + 报告忙碌」时提交保持 `pending`。它不连接 Tern，不证明状态语义；未验证目标仍存在现有启发式的误投风险。
- 决策：不把 `working=false` 当作空闲或安全的证明；在确认字段来源、Agent 类型及状态转换前，不将该字段接入生产投递门。
- 原型保存位置：Git 分支 `prototype/tern-working`，文件 `tern-working-prototype.html`。
